# 记忆优先 AI Agent 架构

记忆成为核心、模型成为可替换执行器的 AI agent 系统的综合设计。

## 1. 核心哲学

### 范式转变

| 维度 | 传统 | 记忆优先 |
|-----------|-------------|--------------|
| **核心** | 模型（能力受限） | 记忆（知识受限） |
| **模型角色** | 大脑 | 可替换的"计算单元" |
| **记忆角色** | 辅助工具 | 一等公民，身份载体 |
| **迁移成本** | 切换模型 = 重新开始 | 切换模型 = 更换执行器 |

### 设计原则

- **记忆 = 内核**：不是附加到模型的缓存，而是系统的核心
- **模型 = CPU**：无状态执行单元，即插即用
- **数据库 = 主板**：连接感知、记忆和执行

## 2. 三角色架构（A/B/C 模型）

### 角色定义

| 角色 | 名称 | 职责 | 特征 |
|------|------|----------------|-----------------|
| **A** | 记忆守护者 | 全局记忆维护 | 长期、持久、跨会话 |
| **B** | 上下文构建者 | 短期记忆 + 上下文组装 | 实时、会话范围、协调器 |
| **C** | 执行者 | 任务执行 | 无状态、纯函数、专注执行 |

### 可选扩展：添加中期"任务记忆"角色（T）

当任务跨越多个上下文窗口时，引入中期记忆层来跟踪计划和进度，而不污染长期事实。

| 角色 | 名称 | 职责 | 特征 |
|------|------|----------------|-----------------|
| **T** | 任务追踪者（中期记忆） | 任务计划/进度状态（计划 → 待办 → 步骤执行 → 完成） | 跨窗口、任务范围、结构化、可恢复 |

映射到 `tp/tr` 工作流：

- `/tp` 创建并持久化计划产物（如 `todo.md`、`state.json`、`plan_log.md`）→ 这是任务的中期规范记忆。
- `/tr` 推进 `state.json.current` 并按步骤更新待办/日志 → 这是中期记忆变更。
- 长期记忆仅通过从任务中提取稳定结果来更新（非进行中状态）。

## 3. 记忆存储架构

### 三级存储（热-温-冷）

| 层级 | 数据类型 | 技术栈 | 设计模式 |
|------|-----------|------------------|----------------|
| **L1: 热** | 当前会话、临时变量、工具输出 | Redis / Memcached | 滑动窗口 + 优先队列，毫秒级读写 |
| **L2: 温** | 任务状态和实体关系 | SQLite / Postgres +（可选）图数据库 | 任务状态机 + 知识图谱 |
| **L3: 冷** | 历史日志、文档块、代码片段 | Pgvector / Chroma / LanceDB | 语义索引 + 时间戳，混合搜索 |

注意：

- 在许多实现中，"L2" 最好分成两个关注点：
  - **中期任务记忆**：强结构化、任务范围（`task_id`）产物，如 `state.json` + `todo.md` + `plan_log.md`。
  - **实体/关系记忆**：可选的跨任务推理图层。

### 数据库选择

| 记忆类型 | 存储方案 | 理由 |
|-------------|------------------|-----------|
| 长期记忆 | ChromaDB/Qdrant + SQLite | 向量检索 + 结构化元数据 |
| 短期记忆 | Redis / 内存中 | 快速读写，TTL 自动过期 |
| 文件索引 | Neo4j / SQLite + 嵌入 | 依赖图 + 语义搜索 |
| 执行状态 | SQLite | 事务性，支持回滚 |


### 核心原则：本地记忆优先

| 记忆类型 | 检索成本 | 延迟 | 一致性 | 用例 |
|-------------|----------------|---------|-----------|----------|
| **本地记忆** | 零 | 零 | 很高 | 连续任务、迭代开发 |
| **全局记忆** | 高 | 高 | 中等 | 跨会话、新任务启动 |

### 三层上下文结构

```
┌─────────────────────────────────────────────────────────────┐
│  第 1 层：系统提示（固定）                 ~5% 预算  │
│  - 角色定义、规则约束                        │
├─────────────────────────────────────────────────────────────┤
│  第 2 层：注入记忆                    ~30-40% 预算 │
│  - 从全局记忆检索                             │
│  - 项目背景、历史决策、相关代码   │
├─────────────────────────────────────────────────────────────┤
│  第 3 层：本地上下文                    ~50-60% 预算 │
│  - 当前会话对话历史                         │
│  - 近期任务链、迭代过程                     │
└─────────────────────────────────────────────────────────────┘
```

## 5. 记忆检索策略

### 添加任务范围检索（中期优先）

如果任务处于活跃状态，检索应在全局长期记忆之前优先处理中期任务产物：

1) 任务状态（`state.json`）：当前步骤、尝试、阻塞原因、完成条件
2) 任务待办（`todo.md`）：剩余工作和完成标记
3) 任务日志（`plan_log.md`）：关键决策和理由
4) 全局长期记忆：稳定事实/偏好/约束

这避免了在上下文窗口重置后浪费上下文预算重新推导"我们在做什么"。

### 多路径检索流

```
用户输入
    │
    ↓
┌─────────────────────────────────────────┐
│  步骤 1：意图识别              │
│  - 意图：bug_fix / new_feature / 等.  │
│  - 领域：auth / payment / 等.         │
│  - 关键词：从查询中提取        │
└─────────────────────────────────────────┘
    │
    ↓
┌─────────────────────────────────────────┐
│  步骤 2：混合检索                │
│  - 向量搜索（语义）              │
│  - 关键词搜索（BM25）            │
│  - 图遍历（结构化）              │
└─────────────────────────────────────────┘
    │
    ↓
┌─────────────────────────────────────────┐
│  步骤 3：排序                        │
│  - 语义相似度 (0.4)             │
│  - 时间衰减 (0.2)               │
│  - 类型匹配 (0.2)               │
│  - 引用频率 (0.2)               │
└─────────────────────────────────────────┘
    │
    ↓
┌─────────────────────────────────────────┐
│  步骤 4：预算分配                │
│  - 必须有：30%                        │
│  - 应该有：50%                        │
│  - 最好有：20%                        │
└─────────────────────────────────────────┘
```

### 基于任务类型的检索优先级

| 任务类型 | 优先级顺序 |
|-----------|----------------|
| Bug 修复 | 错误历史 > 相关代码 > 架构决策 |
| 新功能 | 架构决策 > 用户偏好 > 相关代码 |
| 重构 | 架构决策 > 代码结构 > 变更历史 |
| 问答 | 项目知识 > 历史对话 > 文档 |

## 6. 上下文优化

### 分层缓存策略

```
┌─────────────────────────────────────────────────────────────┐
│  第 0 层：基础上下文（会话级缓存）                │
│  - 系统提示、项目背景、代码结构        │
│  - 更新：仅在项目变更时                          │
├─────────────────────────────────────────────────────────────┤
│  第 1 层：任务上下文（任务级缓存）                │
│  - 任务相关代码文件、相关决策              │
│  - 更新：任务切换时                              │
├─────────────────────────────────────────────────────────────┤
│  第 2 层：增量上下文（无缓存）                    │
│  - 当前任务描述、上次执行结果              │
│  - 更新：每轮                                    │
└─────────────────────────────────────────────────────────────┘
```

### 效率提升

```
第 1 轮：初始组装
- L0：生成 + 缓存 (30K)
- L1：检索 + 缓存 (30K)
- L2：生成 (20K)
- 总成本：80K 生成

第 2 轮+：同一任务链
- L0：复用缓存 ✓ (0 成本)
- L1：复用缓存 ✓ (0 成本)
- L2：仅更新增量 (20K)
- 总成本：20K 生成，60K 复用
- 效率提升：~70%
```

### B 的上下文管理

**问题**：B 每次组装 80K 上下文导致上下文膨胀

**解决方案**：B 只保留"元数据"，而非"完整内容"

| 信息类型 | 存储位置 | B 保留 |
|------------------|------------------|-----------|
| 组装上下文 | 临时变量（使用后丢弃） | "组装了 75K，包含 X/Y/Z" |
| C 的代码输出 | 文件系统 | "生成了 src/auth/token.py" |
| 检索到的记忆 | A 的记忆存储 | "检索到 3 个 auth 相关项" |
| 执行结果 | 文件系统 / 日志 | "成功/失败，原因..." |

## 7. 全局记忆维护

### 维护模式

| 模式 | 维护者 | 触发器 | 优缺点 |
|------|------------|---------|------------|
| **同步** | 当前执行者 | 任务完成时立即 | 实时但增加延迟 |
| **异步** | 专用记忆 Agent | 后台定期清理 | 非阻塞但可能滞后 |
| **混合** | 关键同步 + 细节异步 | 分层触发器 | 平衡效率和完整性 |

### 维护的实际触发器

长期记忆不应每轮都重写。优先在执行期间仅追加候选写入，并在显式生命周期事件上运行整合/压缩：

- **显式**：用户调用 CLI 命令如 `memory clear`
- **隐式**：会话结束 / 重启（`on_session_end` 钩子）
- **里程碑**：任务最终确定 / 步骤完成（写入候选；异步合并）

为了在长期更新是周期性的时候保持在线检索质量，使用双源检索策略：

- **实时层**：当前/附近会话中产生的近期候选（TTL）
- **长期层**：整合事实 + 索引块

查询两者并合并结果。

### 推荐：混合模式

```
任务执行期间
    │
    ├─→ 关键决策/错误 ──→ 同步写入（立即）
    │   - 重要架构决策
    │   - 失败尝试（防止重复）
    │   - 显式用户偏好
    │
    └─→ 常规信息 ──→ 标记待处理 ──→ 异步清理
        - 对话细节
        - 中间过程
        - 代码变更记录

空闲 / 会话结束期间
    │
    └─→ 记忆 Agent 激活
        - 处理待处理信息
        - 合并重复记忆
        - 压缩/总结旧记忆
        - 清理过期信息
```

## 8. 潜在问题和解决方案

### 已知风险

| 风险 | 描述 | 解决方案 |
|------|-------------|----------|
| **检索漂移** | 摘要主导未来检索 → 语义偏移 | 混合检索（语义 + 关键词 + 时间衰减） |
| **自我强化** | 错误记忆被重述 → 变成"真相" | 定期"反思"扫描矛盾 |
| **过度压缩** | 总结丢失约束 → 微妙任务错误 | 同时存储原始和总结；置信度低时包含原始 |
| **记忆垃圾** | 每轮都写入 → 存储膨胀、嘈杂检索 | 选择性写入、重要性评分 |
| **死锁** | 记忆 LLM 等待任务 LLM；任务 LLM 等待记忆 | 带超时的确定性协调器 |
| **隐私泄露** | 敏感数据未经治理存储 | 严格脱敏规则、允许列表字段 |
| **版本偏差** | 两个 LLM 看到不同的系统提示 | 集中式提示管理 |

### 递归问题："谁管理记忆模型的记忆？"

**解决方案：分层和冻结**

- **系统提示**：记忆 LLM 的"元记忆"，不可变的硬编码规则
- **工作记忆**：仅维护非常短的滑动窗口（如最后 5 轮）
- 记忆 LLM 不需要记住"我昨天处理了什么"，只需要"我现在在处理什么"

## 9. 实现建议

### 分阶段方法

| 阶段 | 内容 |
|-------|---------|
| 步骤 1 | 确定性协调器 + 嵌入存储 + 严格模式（事实/偏好/约束/任务） |
| 步骤 2 | 大模型仅用于写入时整合和冲突检查；检索保持廉价 |
| 步骤 3 | 添加记忆"审查"批处理作业来清理/合并记忆 |
| 步骤 4 | 仅在单 LLM 基线证明不足时引入第二个 LLM 用于记忆 |
| 步骤 5 | 实施护栏：版本控制、"真相来源"标签、置信度分数、删除/遗忘路径 |

### CCB 环境映射

| 角色 | CCB 实现 |
|------|-------------------|
| **A (记忆守护者)** | Claude / Codex / 专用记忆 Agent |
| **B (上下文构建者)** | Claude Code（当前会话）- 自然协调器 |
| **C (执行者)** | Codex / Gemini / OpenCode / Claude API |

## 10. 关键洞察

### 来自多模型分析

| 来源 | 核心洞察 |
|--------|--------------|
| **Claude** | 递归问题是核心缺陷；需要固定规则打破无限回归 |
| **Codex** | 技术上可行；需要评估系统和护栏 |
| **OpenCode** | 渐进引入；大模型仅用于关键记忆操作 |
| **Gemini** | 双脑架构最优；分层存储 + 反思机制解决漂移 |

### 最终原则

> **不要让模型"记住" - 让模型"查询"**
>
> 构建一个强大的检索引擎，理解代码结构、关联历史对话并实时更新文件状态。模型只是该引擎的自然语言接口和决策者。
